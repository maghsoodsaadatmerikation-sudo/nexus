# NEXUS v1.9 — Continuous Runtime Conformance & Drift Detection

Status: **IN PROGRESS / FAIL-CLOSED**

v1.9 adds no authorization capability. It repeatedly observes the already-public, explicitly non-authoritative runtime identity and preserves evidence that production has not drifted from the recorded source-tree identity during the stated observation window.

Constitutional invariant: `A_out <= A_in`.

## Fixed observation baseline

- Endpoint: `https://nexus-stage-d-production.up.railway.app/v1/runtime-identity`
- Schema: `nexus.runtime-identity.v1`
- Authority marker: `non_authoritative_build_metadata`
- Expected source-tree SHA-256: `d66021fc1e8c276df2c673d26b05f2de58ef4c81589261cb41aefa1ad047f1c7`
- Watcher baseline commit: `82848b2cf938d397179a9ff4b35662334336a494`

The digest is evidence inherited from the sealed v1.7 runtime-provenance boundary. It is not authority.

## Gates

### G1 — Historical integrity
- v1.7.0 and v1.8.0 remain unchanged.
- v1.9 adds temporal evidence rather than rewriting prior claims.

### G2 — Temporal observation window
- At least three successful **scheduled** `NEXUS v1.9 Runtime Drift Watch` runs must exist for the fixed watcher baseline commit.
- Each accepted run must expose a downloadable `v1.9-runtime-drift-evidence` artifact.
- The release gate re-reads evidence rather than trusting run conclusion alone.

### G3 — Fail-closed conformance
Every accepted observation must record HTTP 200, the exact schema and authority marker above, expected and observed digests exactly equal to the fixed digest, and `digest_match: true`. Missing, malformed, unavailable, ambiguous, or mismatched evidence fails closed.

### G4 — Evidence provenance
Each observation emits JSON evidence plus SHA-256, receives GitHub attestation, and is uploaded as an artifact. Expected and observed identities remain separate fields.

### G5 — Authority and mutation non-expansion
The watcher has no Railway credential or NEXUS bearer token. Every accepted evidence document must record `production_write`, `deployment`, `rollback`, `promotion`, `authorization`, `human_judgment`, and `policy_mutation` as false. No paid resource, new production service, new production volume, secret disclosure, or authority expansion is required.

### G6 — Exact release boundary
The release gate runs only after successful `NEXUS Verification` on main. Release mutation is eligible only when the exact verified commit contains `release-intents/v1.9.0` and its commit message is exactly:

`release(v1.9): request continuous-conformance seal`

The gate requires sealed v1.8.0, refuses an existing v1.9.0 tag, validates at least three scheduled observation artifacts from the fixed watcher baseline, and only then creates v1.9.0 at the exact verified release-intent commit.

## Claim boundary

If every gate passes, v1.9 may claim only that during the recorded accepted observation window the public production runtime identity repeatedly reported the expected source-tree digest with the expected non-authoritative schema/marker and no production mutation recorded by the watcher.

It does not establish continuous availability between observations, provider correctness, absence of unobserved transient drift, universal security, universal availability, formal epistemic correctness, or formal proof of `A_out <= A_in`.

## Completion rule

Fewer than three valid scheduled observations, any digest/schema/authority mismatch, missing evidence, mutation-scope violation, failed exact-candidate verification, or duplicate release tag => **NO SEAL**.
