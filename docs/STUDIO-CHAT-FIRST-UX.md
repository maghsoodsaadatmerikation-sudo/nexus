# Phase 42 — Chat-first, touch-friendly NEXUS Studio navigation

## User problem confirmed in source

The integrated Studio offers more than ten capabilities and 20+ actions on one very long page, but its default 780px breakpoint only stacked every card in a single column. On a phone, people could easily lose the conversation composer among settings, research/code/lab features, and the private archive. There was no clear onboarding when starting with zero projects. The separate public static PWA and the local Termux distribution both package the same source, so improving only the backend gateway would not help.

## Implemented UX

- **Chat-first on phones (viewport width <= 780px):** a focused layout shows just the conversation card. Fixed, thumb-sized bottom navigation exposes **Chat / Projects / Tools / Save** (English-first; Persian labels and RTL layout). All previously supported panels and their controls still exist and can be reached, but advanced cards remain hidden until chosen. Tool chooser opens a ten-tool, two-column-friendly menu for Data analysis, Research, Code, Tasks, Charts, Writing, Sources, Assistant & memory, Astrology and Sky.
- **No destructive layout changes:** panel selection only changes DOM `hidden`, preserving work-in-progress text and the existing application model. The user can choose **Show all sections** to restore the former long layout; desktop continues using that by default. Focus can be manually toggled without updating or persisting the encrypted archive.
- **First-run guidance:** when the session has no project, the conversation shows a short two-step bilingual explanation and **Create a project** action routing to the existing project form. After creating a project but before a conversation exists, the CTA creates a new conversation via the existing reviewed application handler. Once a conversation exists, the prompt disappears. No automatic private data submission, storage, provider request or background task is introduced.
- **Tool-to-chat handoff:** when research/code/data results are explicitly staged using the existing reviewed one-turn excerpt path, the conversation is automatically revealed if the user has chosen focused layout. The text remains temporary, and the same existing explicit model-send consent rules apply. Stage only after a real user action.
- **Access and ergonomics:** panel headings receive focus after switching for screen-reader and keyboard feedback; buttons include `aria-controls`, and current view has `aria-current`. Controls meet a minimum 44px touch height in focus mode. The bottom dock yields to a focused text input so it doesn't cover the phone's keyboard. Existing page status and the truthful temporary/encrypted-saved notice stay visible; tool menus never store prompt or token content. The code renders translation labels with `textContent` only and contains no HTML injection from conversations or documents.

## Self-critique and safeguards

1. **Risk: hiding too much.** Focus mode must not become a feature removal. It is reversible with one button, preserves the preexisting full-layout desktop mode, exposes a complete tool chooser and keeps current controls mounted in the DOM. The tab selection is not a vault mutation.
2. **Risk: silent data loss.** The new UI does not call the project state mutation layer when navigating, and it never reports a session as saved. Existing ephemeral-tab and encrypted-vault warnings remain. Real Chromium tests verify the same draft conversation after switching between chat, tools and Save, plus encrypted reopen after a simulated network outage.
3. **Risk: broken RTL, accessibility or tap ergonomics.** Use language-aware labels, focusable section headings, active navigation semantics, explicit 44px targets, keyboard-aware bottom navigation and scroll-width checks at a 420px viewport. Test Persian labels and RTL in Chromium. Complete WCAG screen-reader/touch accessibility **on real Android hardware** remains unverified.
4. **Risk: on-device local origin & old hosted version mismatch.** The same sources deterministically rebuild `web/studio.html`, `public/studio/index.html`, and the integrity-pinned `public/studio/service-worker.js`; the public Render site does **not** auto-deploy merely because a PR merged. The earlier offline pilot remains separate. The phone-local ZIP can be rebuilt on `main` with the existing source-bound GitHub Action without changing the original Railway Volume.
5. **Risk: mimicking a real model.** No additional generative model is provisioned. The local reflection guide remains visibly non-generative, model connection continues optional and review-based, and no API secret is accepted into a project archive.

The existing full NEXUS Studio tests still run, including model provider consent, memory and archival boundaries.

**Not claimed:** deployed Render upgrade, real Android accessibility audit, hosted frontier-model quality, full app-store installation or authenticated Stage D recovery. No paid service, private key, provider secret, or production `/data` Volume is touched. `A_out <= A_in`.
