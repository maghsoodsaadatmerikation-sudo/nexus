# NEXUS v1.7 Roadmap — Runtime Provenance & Source-Tree Identity

Status: **IN PROGRESS / FAIL-CLOSED**

NEXUS v1.7 follows the sealed v1.6.0 exact-promotion boundary. v1.6 established an explicit provider-side source pin and successful production deployment, but deliberately did not claim that Railway trigger metadata independently proved the selected source or that the running binary was independently reproducible from provider metadata alone.

v1.7 closes a narrower, testable gap: the executable image embeds a deterministic digest of the source/build-input tree, exposes that digest as explicitly non-authoritative runtime metadata, and compares the observed production value against independently computed repository evidence.

## Constitutional invariant

`A_out <= A_in`

Runtime identity metadata may report provenance evidence. It cannot authorize requests, create HumanJudgment, mutate policy, widen execution authority, or substitute for a release decision.

## Source-tree identity boundary

The canonical digest is computed by `scripts/source-tree-digest.sh` over the build inputs that determine the executable/product surface:

- root `Cargo.toml` and `Cargo.lock`;
- `Dockerfile`;
- constitutional-core `src/`;
- `artifact-05/` source and lockfile;
- `web/` assets embedded by the gateway;
- the digest script itself.

Build outputs under `target/` are excluded.

The Docker build computes this digest before compiling and embeds it through `NEXUS_SOURCE_TREE_SHA256`. The running service exposes:

`GET /v1/runtime-identity`

with schema `nexus.runtime-identity.v1`, the embedded source-tree digest, and the explicit authority marker `non_authoritative_build_metadata`.

## Gates

### G1 — Historical integrity
- `v1.6.0` remains immutable.
- v1.7 adds evidence rather than rewriting prior release claims.

### G2 — Deterministic source-tree function
- A single canonical script computes the digest.
- The Docker build consumes that same script.
- Missing build inputs fail closed.

### G3 — Embedded runtime identity
- The executable exposes the embedded digest through a read-only endpoint.
- Runtime identity is labelled non-authoritative.
- No secret value, bearer token, user data, workspace data, or policy decision is exposed by the endpoint.

### G4 — Independent CI reconciliation
- `NEXUS v1.7 Runtime Identity` runs only after a successful `NEXUS Verification` run.
- It checks out the exact verified SHA, independently computes the expected digest, builds the image, starts the service, reads the runtime endpoint, and requires exact digest equality.
- The resulting evidence is attested and uploaded.

### G5 — Production reconciliation
- The existing Railway production service must be pinned to an exact v1.7 runtime target commit.
- A new provider deployment must complete successfully without replacing `/data`, expanding privilege, exposing secrets, or requiring a paid upgrade.
- The observed public runtime digest must exactly equal the independently computed CI digest for that target.

### G6 — Release gate
- Production evidence must identify the exact target commit, provider deployment, durable mount, expected digest, observed runtime digest, and equality result.
- The final release-intent commit must complete `NEXUS Verification` successfully.
- No PASS and no release seal are permitted if any evidence field is absent, ambiguous, or mismatched.

## Claim boundary

If all gates pass, v1.7 may claim that the observed production executable reports a source-tree identity exactly matching the independently computed digest for the recorded target build inputs, under the stated Railway deployment and durable-state boundary.

It may not claim bit-for-bit reproducible binaries across arbitrary builders, formal verification of Railway, universal security, universal availability, or formal proof of epistemic correctness.

## Completion rule

No exact runtime/repository digest match -> no PASS -> no v1.7 seal.
