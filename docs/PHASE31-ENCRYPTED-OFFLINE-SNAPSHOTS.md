# Phase 31 — offline authenticated encryption of signed NEXUS snapshots

## What this implements

The opt-in local script scripts/nexus-operator-snapshot-encryption.py provides
AES-256-GCM authenticated encryption for a verified Phase-30
Ed25519-signed offline operator snapshot. Both encryption and decryption
verify the independently pinned snapshot SHA-256, workspace SHA-256, and
Ed25519 public-key fingerprint, the detached signature, and the full
snapshot contents/journal manifest before creating a new output file.

The encrypted file embeds an authenticated, canonical JSON header containing
schema/version, workspace ID, original ZIP hash, workspace hash, signer-key
fingerprint and a freshly generated 96-bit AES-GCM nonce. The entire header
is used as AEAD associated data. The envelope has a mandatory separately
pinned SHA-256 on decryption. Neither the key nor secrets are logged.

This is an **offline operator-only CLI**, not a hosted storage service, not
automatic disaster recovery, and not an upgrade of NEXUS's public API.

## Critical trust and privacy boundaries

- The AES encryption key is exactly 32 CSPRNG-generated bytes, stored in
  a private 0600 file; the owner must back it up in an independently
  controlled secure location. Loss means loss of encrypted backups.
- A detached Ed25519 signature with an independently pinned public key
  remains mandatory for both encrypt and decrypt. Encryption alone does
  not establish a trusted producer's identity.
- The archive SHA, encrypted-file SHA, workspace SHA and signer-key SHA
  must be copied from independently trusted records, not merely alongside
  ciphertext delivered by an untrusted party.
- Decrypt **does produce a plaintext ZIP** (0600) into a private 0700
  directory; the original plaintext export is also not deleted on encrypt.
  The plaintext ZIP must be protected and disposed of by the operator.
  File deletion is not a guarantee of physical secure erase.
- Metadata in the authenticated envelope header is visible, including
  hashes and workspace ID. Only the ZIP content is encrypted.
- A valid older encrypted signed snapshot can be replayed if old pins are
  accepted. Independent monotonic freshness/anti-rollback controls are
  **not implemented** here.
- Key custody, rotation, loss recovery, signed checkpoint freshness,
  hostile host isolation, independent third-party identity, and platform-
  wide enforcement of signed/encrypted restore remain separate gates.
- No real workspace or key goes to GitHub CI, no hosted agent authority,
  no Docker socket or network service is exposed. Maintain A_out <= A_in.

## Offline operator sequence

Run on a private, nonroot Linux machine with the Python cryptography
package installed, using private owner-only directories (mode 0700).
The dedicated tests install cryptography==46.0.4.

Create the key in a secure, separate, owner-private directory:

~~~bash
umask 077
python3 scripts/nexus-operator-snapshot-encryption.py new-key \
  --key /private/keys/snapshot-aes256.key --approve-new-key
~~~

First create an offline ZIP and detached Ed25519 signature following
docs/PHASE30-SIGNED-OFFLINE-SNAPSHOTS.md. Obtain independent pins
ARCHIVE_SHA256, WORKSPACE_SHA256, and SIGNER_SHA256.

~~~bash
python3 scripts/nexus-operator-snapshot-encryption.py encrypt \
  --archive /private/transfer/snapshot.zip \
  --output /private/transfer/snapshot.sealed \
  --key /private/keys/snapshot-aes256.key \
  --signature /private/transfer/signature.json \
  --public-key /private/keys/signer-public.pem \
  --workspace acceptance \
  --expected-archive-sha256 "$ARCHIVE_SHA256" \
  --expected-workspace-sha256 "$WORKSPACE_SHA256" \
  --expected-signer-sha256 "$SIGNER_SHA256" --approve-encrypt
~~~

Preserve the returned encrypted_sha256 in an independent trusted record.
Transfer the sealed snapshot and detached signature separately from the
encryption key. On the receiving operator host, after separately verifying
trusted fingerprints and key custody:

~~~bash
python3 scripts/nexus-operator-snapshot-encryption.py decrypt \
  --sealed /private/transfer/snapshot.sealed \
  --output /private/transfer/decrypted.zip \
  --key /private/keys/snapshot-aes256.key \
  --signature /private/transfer/signature.json \
  --public-key /private/keys/signer-public.pem \
  --workspace acceptance \
  --expected-sealed-sha256 "$SEALED_SHA256" \
  --expected-archive-sha256 "$ARCHIVE_SHA256" \
  --expected-workspace-sha256 "$WORKSPACE_SHA256" \
  --expected-signer-sha256 "$SIGNER_SHA256" --approve-decrypt
~~~

Use the **separate, explicitly approved** signed restore of Phase 30 on
decrypted.zip. This preserves the finished one-use journal and prevents
replaying a consumed execution approval. Never upload real backups to CI.

## Verification and release policy

The new dedicated workflow operator-encrypted-snapshot.yml performs real
AES-256-GCM encrypt/decrypt, signed snapshot verification, synthetic
full restore and finished-approval anti-replay. Negative tests exercise
altered ciphertext and authenticated-header data (including when the
attacker recomputes an outer SHA-256), incorrect keys, forged signatures,
wrong pins, absent approval, unsafe key permissions, bad key sizes,
symlinked keys and refusal to overwrite existing files.

A PASS is evidence only of this synthetic test contract on the exact
tested commit; not of external key custody, durable disaster recovery or
production readiness. PR #246 is intentionally stacked on draft PR #245
and must not merge or deploy until all required gates pass.
