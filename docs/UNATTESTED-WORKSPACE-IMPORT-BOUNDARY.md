# Unattested machine history: fail-closed workspace import

## Threat and current behavior

A bearer token proves that the user is allowed to call the workspace API. It
**does not** prove that the supplied snapshot, machine adapter, or historical
`MachineAnalysisRecorded` event was generated by the NEXUS server.

A previously well-formed `WorkspaceSnapshot` could include a client-authored
`MachineAnalysisRecorded` event with matching `machine:<adapter>:<run>`
provenance. The core schema can validate event sequencing and matching IDs,
but that validation is not a cryptographic proof of authorship.

As of this change, `POST /v1/workspaces/import` **fails closed** with HTTP
422 and `{"error":"unattested_machine_history_rejected"}` when any incoming
snapshot contains one or more of:

- A claim with origin `MachineAnalysis`.
- An event of kind `MachineAnalysisRecorded`.
- Any event provenance ID starting with `machine:`.

All three are checked separately, **before calling the workspace delegate**.
The actual Rust runtime repeats the same check in its import delegate before
opening or modifying the durable store. Invalid and unauthorized requests
remain subject to existing API authentication and recovery-quarantine gates.

**No signature, signer registry, key, or attestation verifier is invented in
this stage.** Without a trusted key distribution process, the only defensible
default is to reject claims of machine authenticity at the import boundary.

## Supported imports, unchanged data, and compatibility

- Existing persisted workspace snapshots are not migrated or rewritten.
- Internally generated machine events (for example, server-owned local
  question-probe runs) still use the native core recording/storage path.
- The core's pure `WorkspaceEngine::from_snapshot` and repository validators
  still check *structural* validity; these are not HTTP trust enforcement
  mechanisms and do not declare arbitrary snapshots to be authenticated.
- The offline browser's explicitly user-reported output remains importable
  as `ClaimOrigin::ExternalEvidence`, with an `unattested` source label.
- Human-created claims, alternatives, and explicit human judgments remain
  importable and are stored without modifying their content.
- Duplicate workspace imports still return HTTP 409. Rejected machine imports
  do not allocate workspace storage, replace a snapshot, or append events.
- To transfer historical machine output without an attestation system, create
  a *new, separately labeled* unverified-evidence export; never silently
  relabel a signed or original history in place.

## Signed import remains unimplemented

A manual detached Ed25519 signing/verification tool is now available as an
**offline integrity witness**. See [DETACHED-WORKSPACE-ATTESTATION.md](DETACHED-WORKSPACE-ATTESTATION.md).
It does not change this HTTP import denial, register trusted signers, or
establish replay protection.

A secure inter-instance **signed import** still needs all of the following,
**not merely an SHA-256 printed beside the imported file**:

1. A detached, domain-separated Ed25519 signature over a versioned,
   unambiguous canonical representation of the exact snapshot content,
   destination workspace ID and export context.
2. A verifier-side allowlist of trusted **public** keys and key IDs, with
   distinct trust roles for offline import vs. server-generated machine
   events. Key enrollment, revocation and rotation are controlled by
   operators outside user-controlled snapshot JSON.
3. A signature verified **before** the import transaction under bounded
   payload size and strict JSON parsing. Key validity and workspace binding
   must be checked together; one signed snapshot cannot authorize a
   different destination or revision.
4. Anti-rollback/replay checks against durable trusted state, with explicit
   conflict handling, restoration and key-compromise procedures.
5. Real key management: private signing keys must not enter the browser,
   repository, test fixtures, application logs, or a bearer-token-authorized
   API that accepts arbitrary data for signing.

This is a design requirement for a separate feature, **not a claim that
signature verification or historical attestation now exists**.

## Test evidence

Unit regression checks separately classify machine-origin claims, machine
events, and `machine:` prefixes. HTTP tests use an intentionally permissive
delegate to ensure that rejection is enforced at the transport boundary,
and assert that rejected attempts leave the backing store unchanged. A real
disposable Rust HTTP/Docker bridge attempts a structurally valid forged
machine history after a normal offline import, verifies the explicit 422,
and confirms no forged workspace was saved. All ordinary import, authentication,
recovery, browser and persistent-state regression gates must remain green.
