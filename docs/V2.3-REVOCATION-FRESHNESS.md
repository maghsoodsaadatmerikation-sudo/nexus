# NEXUS v2.3 — Revocation Freshness / Stale-Authority Defense

## Purpose

v2.3 prevents an authorization created against one revocation state from being replayed after that state changes.

The boundary preserves:

```text
A_child <= A_parent <= A_in
revocation observed => stale authorization cannot restore authority
```

## Model

`RevocationSet::epoch()` is derived from the length of the validated, ordered revocation event history. It is not accepted as an independent trusted field.

`PolicyEngine::authorize_delegated` produces an opaque `DelegatedAuthorizedRequest` bound to:

- the validated grant identifier;
- the effective authority established by policy;
- the exact revocation epoch observed during authorization.
- the complete validated, ordered revocation snapshot observed during authorization.

`Executor::execute_delegated` requires the current `RevocationSet`. Execution fails closed when the current epoch differs from the authorization epoch or when the grant is revoked.

## Security properties

- A revocation after authorization invalidates the cached authorization.
- An unrelated revocation also advances the epoch and invalidates cached authorization conservatively.
- An older snapshot cannot execute an authorization created against a newer epoch.
- A divergent history with the same epoch cannot execute the authorization.
- Reauthorization at the current epoch can restore executability only for a grant that is not revoked.
- The freshness binding is opaque to callers and cannot be constructed through the public API.
- Evidence and audit observations do not create or restore authority.

## Deliberate non-claims

v2.3 does not claim durable or distributed revocation persistence, cryptographic event authenticity, consensus, linearizability across processes, external identity federation, provider correctness, universal security, or race-free behavior in external systems that do not hold the revocation state stable across their execution boundary.

## Release rule

No exact-candidate canonical verification and v2.3-specific evidence means no PASS and no v2.3 seal. Historical release tags remain immutable.
